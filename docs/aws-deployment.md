# AWS deployment

The Terraform under [`infrastructure/aws`](../infrastructure/aws) is a
**reference implementation** of the topology below — it has not been
applied against a live AWS account from this repository (no account or
credentials are available in this environment, and standing up billed
cloud infrastructure needs an explicit decision from whoever owns the AWS
bill). This document is the guide for actually running it.

## Topology

```
CloudFront (CDN, TLS termination, edge caching for /media/*)
   → Application Load Balancer (path-based routing)
       /api/*  → ECS Fargate service: api
       /*      → ECS Fargate service: web
   → api also reaches, over the private subnets:
       RDS Postgres (Multi-AZ)
       ElastiCache Redis (replication group, encryption in transit + at rest)
       MSK Serverless (IAM-authenticated)
       S3 (media — public via CloudFront OAC; verification docs — private, KMS-encrypted)
       transport-service, via AWS Cloud Map private DNS (transport-service.<name>.internal)
```

## One-time setup before `terraform apply`

1. **Remote state** — uncomment the `backend "s3"` block in `main.tf` and
   create the state bucket + DynamoDB lock table it references (or swap
   in Terraform Cloud/another backend of choice).
2. **ACM certificates** — request a cert for `var.domain_name` in the ALB's
   region, and a second one **in us-east-1** for CloudFront (CloudFront
   only accepts us-east-1 certs regardless of where everything else
   lives). Replace the two `REPLACE_WITH_ACM_CERTIFICATE_ARN*` placeholders
   in `alb.tf` and `cloudfront.tf`.
3. **Container images** — build and push the three images (see
   `infrastructure/docker/*.Dockerfile`) to ECR, then pass their URIs via
   `var.container_images`. A typical CI pipeline: on merge to main, build
   each Dockerfile, tag with the commit SHA, push to ECR, then
   `terraform apply -var='container_images={api="...",transport_service="...",web="..."}'`.
4. **Secrets** — `secrets.tf` creates the Secrets Manager entries but only
   seeds a placeholder `database_url` (RDS's `manage_master_user_password`
   handles the actual DB credential rotation). Populate
   `jwt-access-secret`, `jwt-refresh-secret`, and `razorpay-key-secret`
   manually (`aws secretsmanager put-secret-value`) — they're intentionally
   not generated by Terraform so they never land in state or a `.tf` diff.

## Applying

```bash
cd infrastructure/aws
terraform init
terraform plan  -var='container_images={api="<ecr-uri>",transport_service="<ecr-uri>",web="<ecr-uri>"}'
terraform apply -var='container_images={api="<ecr-uri>",transport_service="<ecr-uri>",web="<ecr-uri>"}'
```

After apply, point `var.domain_name`'s DNS at the CloudFront distribution
(`terraform output cloudfront_domain`), then run
`npm run prisma:deploy` against the new RDS endpoint (from a bastion, an
ECS one-off task, or CI) before the first deploy serves traffic.

## Scaling notes

- `api` and `web` run 2 tasks each by default (`desired_count`), fronted by
  the same ALB via separate target groups — bump `desired_count` or wire
  up an `aws_appautoscaling_target` on CPU/request count per service.
- `transport-service` scales independently of `api` — it has its own ECS
  service and task definition with its own CPU/memory sizing (256/512,
  versus 512/1024 for `api`), reflecting the spec's requirement that
  transportation "scale independently."
- MSK Serverless and Redis's replication group both scale their own way
  (MSK Serverless is capacity-managed by AWS; Redis needs a node-type
  change or `num_cache_clusters` bump, both are `terraform apply`-able
  without downtime for the latter).

## Observability

- Every ECS task logs to the single `/ecs/<project>-<environment>` log
  group (`cloudwatch.tf`) — group by the `awslogs-stream-prefix` (`ecs`)
  and container name to separate `api`/`web`/`transport-service` output.
- Two starter alarms are wired up: elevated ALB 5xx rate on the `api`
  target group, and RDS CPU > 80% for 3 consecutive periods. Extend
  `cloudwatch.tf` with alarms on ECS service CPU/memory, MSK consumer
  lag, and Redis eviction rate before calling this production-ready.
- Health checks: `GET /health` (api, transport-service) and `GET /`
  (web) — both already wired into the ALB target groups and the local
  Docker Compose healthchecks, so the same check is exercised in every
  environment.

## What's intentionally not here

Multi-region failover, WAF rules, a CI/CD pipeline definition, and
blue/green deployment configuration are all real production concerns for
a platform handling payments and personal data, but are out of scope for
this reference — they're deployment-process decisions a team makes once,
not infrastructure this project needs to prescribe.
